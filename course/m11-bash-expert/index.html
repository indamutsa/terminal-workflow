    Write Bash functions, cut up strings and keep lists in arrays

    Reuse a command in a function, remove .txt from a file name, keep file names with spaces in a list, loop over every array item

    The one idea

    Repeat a task: write a function. Cut up text: use an expansion. Keep a list: use an array.

    • Call a function with an argument → greet Ada. Inside the function, $1 is this call's first argument.
    • Save a function's output in a variable → value=$(fn). return sets a status; echo prints text.
    • Remove .txt from a file name → ${f%.txt}. It removes the shortest matching suffix.
    • Pass every array item as its own argument → "${a[@]}". Each value stays one argument.
    The problem

    Why does my helper function change a variable in the main script? Why does my list lose file names with spaces?

    The fix: Keep helper variables local. Store lists in arrays and expand them with "${a[@]}".
    Type it

    Reuse a command with a function

    Start Bash first: type bash. Run this page's blocks in order in that shell. Type exit to go back to zsh.

    Return text or a number from a function: return takes a status from 0 to 255, not a string. echo or printf sends data to stdout. $(fn) captures stdout and strips trailing newlines. It runs in a subshell, so variable changes there do not reach the caller. A function without return uses its last command's status.

    Type it

    Cut, slice and replace text in a variable

    Change a file name or text held in a variable. These expansions change the value you print. They do not rename a file.

    Remove the start or end of a value: # removes a matching prefix and % a matching suffix. Double them to remove the longest match. The pattern is a shell glob. ${p%/*} stays unchanged if p has no slash; use dirname when you need that case handled.

    Why does ${s^^} fail on my Mac? macOS /bin/bash is 3.2 here. ${s^^} for uppercase and ${s,,} for lowercase are Bash 4+ only. Many GNU/Linux systems have a newer Bash; tr works on both. These LC_ALL=C examples convert ASCII letters.

    Type it

    Keep a list of values in an array

    Keep every value in a list whole: an indexed array starts at 0. Use [@] inside quotes to keep each value whole.

    Read file names safely: a line list keeps spaces and backslashes but cannot encode a newline inside a filename. find -print0 and read -d '' use NUL separators, so the array preserves those names too. Sorting printed names here only makes these sample results stable. mapfile is Bash 4+ only. Page 3 explains < <(command).

    Make a Bash script stop on errors and clean up after itself

    Stop a script when a command fails, catch unset variables, clean up temp files on exit, show the line that failed, trace what ran

    The one idea

    Make a script stop when something fails: turn on the failure checks, then handle expected failures explicitly.

    • Stop on a failed command, an unset variable or a broken pipe → set -euo pipefail. Failed commands, unset values and broken pipelines.
    • Run cleanup when a script ends → trap cleanup EXIT. Keep the script's original exit status.
    • Show which line failed → trap ... ERR. Use set -E to inherit ERR in functions.
    • See every command a script runs → bash -x trace.sh. It prints each expanded command on stderr.
    The problem

    Why does my script keep going after a failed step, leave temp files in the working folder and still report success?

    The fix: Catch unexpected failure, keep an EXIT cleanup and use explicit checks for expected failure.
    Type it

    Stop a script at the first error

    Start Bash first: type bash. Run this page's blocks in order in that shell. Type exit to go back to zsh. The options below run in child shells so your interactive shell stays open.

    Why did set -e not stop my script? -e stops on eligible failures; -u rejects unset values; pipefail makes a pipeline return the rightmost nonzero status. -e and ERR skip failures tested by if, while, ! and most && / || lists. A function called as a condition also runs without errexit protection. Check important steps explicitly there. -u still allows empty values, so validate required input too.

    Type it

    Clean up temp files and show which line failed

    Run cleanup whether the script works or fails: put it in EXIT. This exercise moves work to retained/ instead of deleting it.

    Make a private temp folder and clean up on exit: mktemp -d creates a unique private directory. An EXIT trap runs on normal shell exit, including exit after -e; it cannot run after SIGKILL or a power loss. Capture $? before cleanup commands overwrite it. The retained files remain available for inspection.

    What do grep's exit codes mean? For grep, 0 means found, 1 means no match and 2 means an error. A fallback after || runs for any failure: distinguish statuses if they need different handling. Save $? before printing anything.

    Type it

    See which commands a script ran

    Trace a whole script, or just the part you are checking.

    Why does a trace show my values? Tracing prints expanded arguments, so enable it only around values that are safe to display. set +x stops the trace.

    How do I install ShellCheck? On macOS use brew install shellcheck; on Debian/Ubuntu use sudo apt install shellcheck. Then run shellcheck trace.sh. Installation and lint results are not assumed here. Bash 3.2 supports all options and traps on this page.

    Redirect output, type multi-line text and compare command output

    Save output and errors to a file, see output and save it, feed text to a command, compare the output of two commands

    The one idea

    Send output to a file or the screen: redirections run left to right. Choose a stream, then choose its destination.

    • Save output and errors in one file → cmd > run.log 2>&1. Both streams reach the same file.
    • See output on screen and save it to a file → cmd | tee run.log. tee copies stdin to the screen and a file.
    • Type multi-line text with no $ expansion (here-doc) → <<'EOF'. No dollar or command expansion.
    • Compare the output of two commands → diff <(cmd1) <(cmd2). Two readable paths replace temporary files.
    The problem

    Why do errors still print on the screen after I redirect output? Why does a piped loop lose its counter?

    The fix: Redirect stdout before copying stderr. Feed a loop with < <(cmd) to keep its state.
    Type it

    Send output or errors to a file

    Start Bash first: type bash. Run this page's blocks in order in that shell. Type exit to go back to zsh.

    Does the order of redirections matter? With 2>&1 > file, stderr copies the current stdout destination, then only stdout moves to the file. With > file 2>&1, both reach the file. > replaces existing contents; >> appends. &> is Bash syntax. The portable shell form is > file 2>&1.

    Type it

    Type multi-line text into a command (here-doc)

    Feed lines of text to a command: a here-doc ends at its delimiter on a line by itself. Quotes on the delimiter control expansion.

    Why does my indented here-doc fail? The two indented lines above start with actual tabs. <<- strips leading tabs from the body and delimiter, but does not strip spaces. The copy button preserves those tabs.

    Does <<< add a newline? A here-string adds a newline. Here-strings and process substitution work in Bash 3.2 on macOS and in Bash on GNU/Linux; they are not POSIX sh syntax.

    Type it

    Use a command's output as a file, or log a whole script

    Use one command's output as a file: <(cmd) supplies a readable path. The separate < before it redirects that path into a loop.

    What does diff's exit code mean? Diff returns 0 for equal inputs, 1 for differences and a larger status for trouble. Process substitution's producer status is not returned by diff and is not covered by pipefail; use checked intermediate files when producer failure must stop the job.

    Log everything a script prints. Use exec > logfile 2>&1 inside a script: it changes that shell's streams for all later commands. Running logall.sh as a child keeps your interactive prompt attached to the terminal.

    Copy ready-made Bash scripts for backup, rename, retry and confirm

    Back up a folder, rename many files at once, run a command on every file, read flags, retry a failed command, ask before continuing

    The one idea

    Copy one small script per job. Preview changes and check failures before continuing.

    • Back up a folder → bash backup.sh source. It saves the files in a dated tar archive.
    • Preview renaming many files → bash rename.sh. Apply only after reading the dry run.
    • Retry a failed command → bash retry.sh 3 1 cmd. Limit attempts and pause between them.
    • Ask yes or no before continuing → bash confirm.sh. Only yes or y proceeds.
    The problem

    Why did my quick command overwrite a file, retry forever or keep going after I said no?

    The fix: Keep a dry-run default, reject collisions, cap retries and treat EOF as a declined confirmation.
    Type it

    Back up a folder and preview a rename

    Start Bash first: type bash. Run this page's blocks in order in that shell. Type exit to go back to zsh. Each example creates its script with a quoted here-doc and runs it with bash.

    Will a second backup overwrite the first? No. The archive name contains today's date and a unique suffix, so a second run cannot overwrite an older backup. tar -tzf lists its contents without extracting. The printed name varies per run. BSD tar can preserve macOS metadata; GNU tar on Linux may show different metadata entries for real folders.

    Check the rename before you apply it. Read the first two preview lines before running bash rename.sh --apply. The example then prints the applied renames and final names. A collision stops the script; earlier renames are not rolled back. mv -n also avoids overwriting if a destination appears after the check.

    Type it

    Reuse a flag parser: the input parsing is the pattern from Bash basics, now packaged as a reusable script.

    How many times does retry.sh try? N counts total attempts, including the first. Only failed attempts with another attempt left sleep. The final failure returns the command's status. Use retries for commands that are safe to repeat. A command or function tested in if must handle its own internal failures.

    Answer the prompt by hand: run bash confirm.sh at the terminal. The prompt uses printf, so it also appears when input is piped. Empty input, EOF and answers outside the listed yes forms cancel.
