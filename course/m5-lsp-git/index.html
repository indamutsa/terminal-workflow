    Navigate code with LSP

    Jump to definitions and references, and read diagnostics without leaving the editor.

    The one idea

    The language server knows what your code means. Ask it instead of searching text.

    • Definition → gd. Jump to where a name is defined.
    • References → gr. List every real use of a name.
    • Next problem → ]d. Jump to the next error or warning.
    • Jump back → Ctrl-o. Return to where you started.
    The problem

    You grep the project for a function name and wade through comments, strings and unrelated matches.

    The fix: Ask the language server. gd jumps to the definition and gr lists the real references.
    Type it

    Open the practice project

    Every exercise runs against nvim-drills: a small Python project with bad names, an off-by-one bug, unused imports and a failing test. This lesson is for LazyVim, where the leader key is Space.

    Work top to bottom. Do the git exercises on page 2 before the calc rename on page 3, because the reset script would silently undo your rename.

    Type it

    Navigation

    LSP is already configured per language. Open a file and it works.

    Neovim 0.11 also ships native gr* LSP maps that work alongside the above: grn rename, gra code action, grr references, gri implementation, grt type definition. Use gd and gr as your primaries; the gr* set is a fallback.

    Git inside Neovim

    Stage hunks, commit from LazyGit and review changes in Diffview.

    The one idea

    Review and stage changes where you edit, one hunk at a time.

    • Next hunk → ]h. Jump to the next changed block.
    • Stage hunk → <Space>ghs. Stage only that block.
    • LazyGit → <Space>gg. The full git UI inside Neovim.
    • Diffview → <Space>gv. A side-by-side view of the working tree.
    The problem

    You stage whole files with git add, then discover half the change was a leftover experiment.

    The fix: Stage and discard hunk by hunk with gitsigns, and commit from LazyGit.
    Type it

    Gitsigns: inline changes

    Changed lines are marked in the gutter. These keys act on the block under the cursor.

    Inline blame is already on: pause on a line for 300 ms and its author, relative time and commit summary appear at the end of the line.

    Type it

    Stage one hunk, discard another

    Open a terminal with <Space>ft in the nvim-drills root and reset the repo to a dirty state.

    Type it

    LazyGit: the full git UI

    A complete git interface in a float. Press ? inside it for every key.

    Type it

    Snacks git pickers

    Fuzzy lists for logs, history, status and diffs.

    The GitHub issue and pull-request pickers need the GitHub CLI and access to the repository.

    Type it

    Diffview: side-by-side diffs and history

    Your Diffview setup uses its own mappings, which do not overlap with the Snacks diff pickers.

    Safety: never press X in Diffview. It restores the selected entry to the left-side state and can remove an untracked file. This conflicts with the no-delete rule.

    Want a clean slate later? Run ./scripts/reset-dirty.sh from the nvim-drills root: the purpose-built reset path.

    Refactor, files and project search

    Rename across the project, manage files, replace everywhere and search with pickers.

    The one idea

    Change a name once and let the tools update every use.

    • Rename symbol → <Space>cr. Updates every reference in the project.
    • Replace everywhere → <Space>sr. A preview panel for project-wide replace.
    • Grep → <Space>sg. Search file contents.
    • To quickfix → Ctrl-q. Send every picker result to a list.
    The problem

    You rename a function with find-and-replace and also change a variable, a comment and a file name that merely look alike.

    The fix: Use the language server to rename a symbol, and grug-far to preview every text match before it changes.
    Type it

    LSP actions: rename a symbol

    Rename, fix and format from one prefix.

    Inlay hints (inline type annotations) toggle under <Space>u, the UI toggles menu. Verify the exact subkey in the <Space> which-key menu.

    Do not verify with a plain <Space>sg calc grep. It also matches the local variable calc = Calculator() in tests/test_calculator.py. gr is scope-aware.

    Type it

    File management

    LazyVim does not ship Oil.nvim. File management is the Snacks explorer, opened with <Space>e or `.

    The snacks explorer gives you picker-style navigation plus add, rename and delete on the highlighted entry. For bulk renames, use a shell :!mv command.

    Type it

    Search and replace across the project

    LazyVim uses grug-far, not Spectre.

    In grug-far you preview all matches grouped by file and can edit the buffer to fine-tune the replacement. Plain :%s/old/new/g (current file) and :cdo s/old/new/g (over a quickfix list) still work for ad-hoc replaces.

    Type it

    Terminals

    Ctrl-` and Ctrl-/ toggle the last terminal you used. The <Space>tf, <Space>tv and <Space>th keys open a float, a right and a bottom terminal. All of them open in :pwd.

    Each of the three keeps its own terminal. <Space>t also holds the test keys (neotest), and <Space>1..<Space>9 are Harpoon file jumps, not terminals.

    Open the terminal with <Space>ft, hide it with Ctrl-\ Ctrl-n then <Space>ft, and bring it back with <Space>ft. If the venv is not active, use python3 -m pytest.

    Type it

    Fuzzy finder (snacks picker)

    LazyVim uses the snacks picker, not Telescope.

    In the current config the find keys (<Space><Space>, <Space>ff, <Space>sf) and the grep keys (<Space>/, <Space>sg, <Space>sw) search :pwd, not the project root.

    These are the snacks defaults. If one does not match, press ? inside the picker to see its live keymap.

    Tests and the debugger

    Run a test file, read the failure and step through a real bug.

    The one idea

    Run tests and debug without leaving the editor.

    • Run the file → <Space>tt. Run every test in the current file.
    • Run nearest → <Space>tr. Run only the test under the cursor.
    • Breakpoint → <Space>db. Stop on this line.
    • Debug a test → <Space>td. Run the nearest test under the debugger.
    The problem

    A test fails and you scatter print() calls through the code to see why.

    The fix: Set a breakpoint, debug the test, and watch the variables change as you step.
    Type it

    Neotest: run a file, read the failure

    Results show inline, and you can jump to failures.

    Type it

    Stop the debugger with <Space>dt (terminate) or close the UI with <Space>du.

    Type it
