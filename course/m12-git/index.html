    Save my work with git: stage, commit and see what changed

    Save my work, see what changed before I commit, commit only part of a file, look at my history

    The one idea

    Save a snapshot of your project: look at what changed, choose the changes, commit them with a message.

    • See what changed → git status. Add -s for one short line per file.
    • Choose what to save → git add file. Add -p to pick single changes inside a file.
    • Save a snapshot → git commit -m "message". Every commit gets a short hash.
    • Look at my history → git log --oneline. Add --graph to see branches.
    The problem

    How do I save my work with git? You edit files all day, and you cannot tell which edits are saved, which are only chosen and which are still loose.

    The fix: Run git status to see it, git add to choose, git commit to save. Each commit is a snapshot you can come back to.
    Type it

    Start a git repository and make my first commits

    The hub is just a folder that works like GitHub. Clone it into /tmp/tw-git/shop, where the four pages run in order. Git needs a name and email on each commit: this block sets them for this repo only.

    To start over, move /tmp/tw-git to an unused backup name with mv, then run the block again. A bare hub stores history without editable project files; edit in shop and push to the hub. If Git says "Please tell me who you are", set user.name and user.email in the repo as above.

    Type it

    See what I changed before I commit (git status, git diff)

    Look first, then save. git status lists the files. git diff shows the lines.

    git restore file cannot be undone: the edit was never committed, so git has no copy of it.

    Type it

    Commit my changes with a message (git commit)

    Commit what is staged. Write the message as what the commit does: "Add order A5", not "changes".

    To save every edit to files git already tracks in one step, use git commit -am "message". It skips new files, so run git add for those first.

    git add -p shows one change at a time and asks what to do. Press y to stage it, n to skip it, s to split a big change, q to stop. Git asks about each change in turn, so the second change here gets its answer too.

    Type it

    Look at my history (git log, git show)

    Read the commits you made. Git opens long output in a pager: press q to leave it.

    2. Keys: git status -s · Check what changed.

    Undo a mistake in git: unstage, amend, undo a commit, get it back

    Unstage a file, fix my last commit message, undo my last commit, get back a lost commit, put changes aside with stash

    The one idea

    Pick the undo by what went wrong. Soft and mixed reset keep your edits. Plain restore and hard reset overwrite them.

    • Unstage a file → git restore --staged file. The edit stays in the file.
    • Fix my last commit → git commit --amend. Add -m to change the message.
    • Undo my last commit → git reset --soft HEAD~1. The changes stay staged.
    • Get a lost commit back → git reflog. Find its hash, then make a branch there.
    The problem

    How do I undo a git mistake? You staged the wrong file, typed a message wrong or committed too early. Each mistake has its own fix, and the wrong one loses work.

    The fix: Match the mistake to the command in the rules below. git restore --staged, soft reset and mixed reset keep your working files. Plain restore overwrites unstaged edits. Reflog entries expire after 90 days by default, or 30 days for unreachable entries. Your config can shorten these times.
    Type it

    Unstage a file or get an old version back (git restore)

    git restore has two jobs: take a file off the staging area, or bring back an older copy of it.

    Type it

    Fix my last commit: message or forgotten change (git commit --amend)

    Amend replaces the last commit with a new one. Use it before you push, never after: a pushed commit is shared.

    Type it

    Undo my last commit and keep my changes (git reset)

    git reset HEAD~1 moves the branch back one commit. Use reset only before you push that commit; use revert for pushed commits. The flag decides what happens to your changes. These commits stay local until the next drill.

    Type it

    Get back a lost commit or undo a shared one (git reflog, git revert)

    A commit you reset away is not gone. git reflog lists every place HEAD has been. A commit that others already have needs git revert, which adds a new commit instead of rewriting history.

    Type it

    Save my changes for later without committing (git stash)

    Stash clears your edits so you can switch tasks. Bring them back when you are ready.

    A plain git stash skips new files that git does not track yet. Add -u to stash them too: git stash push -u -m "message".

    Rules and review depth

    Which command undoes which git mistake

    01Match the mistake to the undo

    Start with the smallest fix.

    What went wrongCommand
    I edited a file and want the old textgit restore file
    I staged the wrong filegit restore --staged file
    My last commit message has a typogit commit --amend -m "new message"
    I committed too earlygit reset --soft HEAD~1
    I need to undo a commit others havegit revert HEAD
    I lost a commitgit reflog, then git branch recovered <hash>
    02What each git reset keeps

    All three move the branch back. They differ in what they do to your work.

    CommandStaged changesFiles
    git reset --soft HEAD~1KeptKept
    git reset HEAD~1UnstagedKept
    git reset --hard HEAD~1DeletedDeleted
    03Rewrite a commit or add a new one

    Amend and reset only before you push; revert a pushed commit.

    CommandUse it when
    git commit --amendThe commit is only on your machine
    git resetThe commit is only on your machine
    git revertThe commit is pushed or shared

    Undo a commit I made too early

    The setup

    1. Keys: git reset --soft HEAD~1 · Undo the commit. The changes stay staged.
    2. Keys: git status -s · Check: the file shows as staged.

    step-by-step solution

    2. Push the new commit as usual.
    Final answer: git revert --no-edit HEAD adds a commit that reverses the last one.

    step-by-step solution

    2. Add -u to include untracked files.
    Final answer: Use git stash push -u.

    Create, switch and merge a git branch and fix a merge conflict

    Create a branch, switch branches, merge a branch into main, fix a merge conflict, rebase, cherry-pick, delete a branch

    The one idea

    Work on a copy of the history, then bring it back. Branches are cheap: make one for every task.

    • Create a branch and switch to it → git switch -c name. Switch back with git switch main.
    • Merge a branch into main → git merge name. Run it while main is checked out.
    • Fix a merge conflict → git add file. Edit the file first, then add it and commit.
    • Copy one commit to another branch → git cherry-pick name. Use a commit hash for any commit.
    The problem

    How do I try something without breaking main? You edit on main, and a half-done change gets mixed with the fixes you need to ship.

    The fix: Make a branch for the change, commit there, and merge it when it works. If two branches change the same line, git asks you to choose.
    Type it

    Create a branch and switch between branches (git switch)

    A branch is a name for a line of commits. Switching changes the files in your folder to match.

    Type it

    Merge a branch into main (git merge)

    Check out the branch that should receive the work, then name the branch to bring in. Git may open an editor with a merge message: save and close it, or add --no-edit to skip it.

    Type it

    Fix a merge conflict

    A conflict happens when two branches change the same line. Git stops, marks both versions in the file and waits for you.

    In a real conflict, open the file in Neovim, delete the marker lines and the version you do not want, then save. The sed line does the same job here, so the block gives the same result every time. To back out of a merge, run git merge --abort.

    Type it

    Put my branch's commits on top of the latest main (git rebase)

    Rebase replays your commits after the newest commit of another branch. The history becomes one straight line instead of a fork and a merge. Rebase only commits that are not pushed yet.

    Type it

    Copy one commit to another branch, or get a deleted branch back

    git cherry-pick copies a single commit. A deleted branch is only a lost name: its commits are still in the reflog.

    Rules and review depth

    Which branch command to use, and how to fix a conflict

    01List, create, switch and delete branches

    Names go after the command.

    CommandDoes
    git branchList branches; the current one has a *
    git switch nameGo to a branch
    git switch -c nameCreate a branch and go to it
    git branch -d nameDelete a branch that is merged
    git branch -D nameDelete a branch even if it is not merged
    02Bring work together: merge, rebase or cherry-pick

    All three move commits. The history looks different afterwards.

    CommandHistory afterwards
    git merge nameFast-forwards when possible; otherwise joins diverged histories with a merge commit
    git rebase mainReplays your branch commits on top of main with new hashes
    git cherry-pick hashOne commit copied, with a new hash
    03Fix a merge conflict in four steps

    Git marks the file with <<<<<<<, ======= and >>>>>>>.

    StepDo
    1git status -s and find the files marked UU
    2Edit each file: keep what you want, delete the marker lines
    3git add file
    4git commit --no-edit, or git merge --abort to give up
    Worked application

    Merge two branches that changed the same line

    The setup

    Two branches set a different price for A1 pen. Finish the merge and keep the price from main.

    1. Keys: git status -s · Find the file marked UU.
    2. Keys: Edit orders.txt · Delete the marker lines and the line you do not want.
    3. Keys: git add orders.txt · Tell git the conflict is solved.
    4. Keys: git commit --no-edit · Finish the merge with git's own message.
    You see
    UU orders.txt
[main 7faf737] Merge branch 'fix-price'
    Why it matters: A conflict is git asking a question. Answer it in the file, then add and commit.

    Push to GitHub, pull changes and fix a rejected git push

    Push my project to GitHub, clone a repository, pull the latest changes, fix a rejected push, tag a release, find who changed a line

    The one idea

    Your history lives on your machine, and a copy lives on a remote. Send yours with push. Get theirs with fetch or pull.

    • Download a repository → git clone url. It makes a folder and sets origin.
    • Get the latest changes → git pull --rebase. git fetch only looks and leaves your files alone.
    • Upload my commits → git push. Use git push -u origin main the first time.
    • Find who changed a line → git blame file. Add -L 1,5 for lines 1 to 5.
    The problem

    How do I share my commits and get my teammates' commits? Your repo is only on your machine until you push it, and a push fails when someone pushed first.

    The fix: Push to origin, fetch to look, and git pull --rebase to put their commits under yours. Here origin is a folder on your disk; GitHub works the same way.
    Type it

    See where git push goes

    You have pushed to the hub since page 1. Check its address and which remote branch each local branch tracks.

    This is the alternative for a fresh repo with no origin; skip it during this exercise. Create the empty repository on GitHub first, then copy its address from the green Code button. Use that address in place of YOUR-NAME/shop.git. If origin already exists, use git remote set-url origin <url> instead of git remote add, with the GitHub address in place of <url>. After -u, a plain git push and git pull know where to go.

    Type it

    Clone a repo from GitHub (git clone)

    Clone makes a folder with the full history and sets origin for you. This block clones the repo for a second person, Alex, who then pushes a commit.

    Type it

    Get the newest changes from GitHub (git fetch, git pull --rebase)

    Go back to your own repo. Alex pushed a commit that you do not have. If a rebase stops for conflicts, fix the files, run git add <file>, then git rebase --continue. Repeat until it finishes, then push. Use git rebase --abort to cancel.

    Type it

    Tag a release (git tag)

    A tag is a name for one commit, such as v1.0. Tags are not pushed with git push: push them by name.

    Type it

    Find who changed a line and when (git blame, git log -S)

    Blame shows who last changed each line. The search option -S finds commits where the number of occurrences of a piece of text changed.

    2. Push the tag by name.
    Final answer: git push origin v1.0, or git push --tags for every tag.
