    Sessions that outlive the window

    Start a tmux session, detach, and come back to everything still running.

    The one idea

    tmux keeps your terminal alive. Close the window and the work keeps running.

    • Start a session → tmux new -s main. Opens a session named main.
    • Prefix → Ctrl-a. Tells tmux that the next key is a tmux command.
    • Detach → Ctrl-a d. Leaves tmux. The session keeps running.
    • Reattach → tmux attach. Brings back everything where you left it.
    The problem

    You close the terminal, or the laptop sleeps, and the running processes are gone.

    The fix: Run everything inside a tmux session. Detach with Ctrl-a d, and tmux attach brings it all back.

    Windows and panes

    One window per job, split into panes when you need two views.

    The one idea

    A session holds windows. A window holds panes.

    • New window → Ctrl-a c. One window per job: editor, tests, agent.
    • Switch window → Ctrl-a w. A picker with a live preview.
    • Split → Ctrl-a |. Two panes side by side.
    • Zoom → Ctrl-a z. One pane fills the screen. Press again to unzoom.
    The problem

    One terminal, three jobs. The editor, the tests and your AI agent fight for the same screen.

    The fix: Give each job its own window, and split a window into panes to see two things at once.

    Copy mode, the command line and fzf

    Copy from scrollback, edit the prompt fast, and fuzzy-find anything.

    The one idea

    Three tools remove most mouse work: copy mode, readline keys and fzf.

    • Copy mode → Ctrl-a [. Move through scrollback with vim keys.
    • Clear the line → Ctrl-u. Deletes the whole line.
    • Fuzzy find → fzf. A filterable list of files.
    • History → Ctrl+R. Search your command history.
    The problem

    You copy output with the mouse and grab half a border, or retype a long path from history.

    Make tmux yours

    Style the status bar, add plugins, and restore your workspace after a reboot.

    The one idea

    One file, `~/.config/tmux/tmux.conf`, controls how tmux looks and behaves.

    • Reload → Ctrl-a r. Applies your config changes.
    • Install plugins → Ctrl-a I. Capital I, with TPM.
    • Save → Ctrl-a Ctrl-s. Saves windows, panes and layout.
    • Restore → Ctrl-a Ctrl-r. Brings the saved workspace back.
    The problem

    A computer restart kills the tmux server, and your windows are gone.

    The fix: Save with resurrect and continuum, then restore once at login with a lock-guarded script.

    tmux-resurrect (save/restore sessions)

    Your entire workspace survives reboots: windows, pane layouts, even running commands.

    The reboot problem. Quitting and reopening iTerm2 is fine: the tmux server keeps running. A computer restart kills the server, and nothing restarts it, so nothing restores.

    The pileup trap. resurrect is not idempotent: every restore trigger re-adds panes. With @continuum-restore 'on', a boot agent and iTerm2 launching tmux, each fires a restore, and the same panes stack 3-6 times into slivers. The fix is exactly one restore, lock-guarded.

    Restore after reboot

    01How it works on boot

    One path, zero pileup.

    StepWhat happens
    1. Log inlaunchd runs boot-restore.sh: starts the server and restores main once, lock-guarded
    2. Open iTerm2tmux new-session -A -s main attaches to the restored session
    3. No re-runsContinuum restore is off and the lock blocks repeats
    02Gotchas

    Four things that bit.

    GotchaFix
    launchd's PATH excludes /opt/homebrew/bin, so resurrect's bare tmux calls fail silentlyExport PATH in the boot script
    tmux start-server alone can exit with no session attachedAnchor it with new-session -d -s main
    Plist Label contains .plist or is not reverse-DNSUse com.you.name
    Both @continuum-restore 'on' and the boot agentThat is the pileup. Pick the lock-guarded path
    03Why not continuum-boot?

    It starts on boot, but opens Terminal.app on every login and still races with iTerm2.
